# 架构审查与重构复盘

**日期**: 2026-05-14  
**项目**: english-reader（英文阅读学习应用）  
**类型**: 系统性架构审查 + 8 项重构修复  
**Commits**: `197d07f` ~ `826ee43`（共 7 个）

---

## 一、审查发现的原始问题

### 1. 耦合度

| 问题 | 严重度 | 详情 |
|------|--------|------|
| AppContext 上帝对象 | 🔴 高 | 一个 Context 管理 6 个不相关的功能域（熟词/生词收藏/文章收藏/已读/高亮/精读），25 个暴露值，任何值变化导致 13 个消费者全量重渲染 |
| vocabCache 模块全局变量 | 🟡 中 | `let vocabCache = null` 隐式共享状态，无失效机制 |
| ArticleReadMarker 隐形副作用 | 🟡 中 | 渲染 `null`，纯靠 useEffect 标记已读，调用方不可见 |
| 组件职责过重 | 🟡 中 | ArticleBody 同时处理：段落解析、标题渲染、高亮标记、弹窗状态、滚动关闭、精读选择、鼠标延迟——7 个职责 |

### 2. 代码质量

| 问题 | 严重度 | 详情 |
|------|--------|------|
| 难度颜色/标签 8 处重复 | 🔴 高 | 同一套 cet4/cet6/postgrad 配色在 vocab.ts、ArticleCard、FilterBar、DifficultyLegend、KnownWordsPage、CollectionPage、article page 等 8 个位置各自定义 |
| 色值硬编码 | 🟡 中 | CSS 变量定义了 6 个但组件不用，全项目 44 个独立 hex 散落在 JSX 里，换主题等于重写所有组件 |
| HighlightToggle / CloseReadingToggle 99% 重复 | 🟢 低 | 两个文件 22 行中 17 行相同，仅 3 处不同 |
| Storage 18 函数重复样板 | 🟢 低 | 每个函数重复 try/catch + JSON.parse + JSON.stringify + typeof window 检查 |
| 命名不一致 | 🟢 低 | markKnown（无 As）vs markAsRead（有 As），saveWordToCollection vs saveWord（storage 层名不同） |

### 3. 可扩展性

| 问题 | 严重度 | 详情 |
|------|--------|------|
| Storage 零抽象 | 🔴 高 | 裸调 localStorage，无 Repository 接口，接入后端需重写全部 18 个函数 |
| 无 Error Boundary / loading.tsx | 🟡 中 | 组件崩溃 = 白屏，无骨架屏 |

## 二、执行的修复（按优先级排序）

### 修复 1：统一难度配置（commit `197d07f`）

**问题**: 难度等级的颜色/标签/描述在 8 个文件各自独立定义，加新难度需改 8 处。

**做法**:
- 新建 `src/config/difficulty.ts`，导出 `DIFFICULTY_STYLE`（颜色+标签+描述）、`getHighlightClass()`（内联高亮样式）、`getDotColor()`（圆点颜色）、`getDifficultyLabel()`（中文标签）、`getBadgeClass()`（徽章样式）、`DIFFICULTY_FILTERS`（含"全部"选项的筛选按钮配置）
- 更新 `vocab.ts`：删除本地 3 个 Record + 3 个函数，改为从 config 导入后重新导出（保持函数签名兼容，消费者 import 路径不变）
- 更新 `ArticleCard.tsx`：删除 `DIFFICULTY_STYLES`，改用 `getBadgeClass()`
- 更新 `FilterBar.tsx`：删除 `DIFFICULTIES` 数组，改用 `DIFFICULTY_FILTERS`
- 更新 `DifficultyLegend.tsx`：删除 `LEGEND` 数组，改用 `DIFFICULTY_STYLE`
- 更新 `KnownWordsPage.tsx`：删除 `DIFFICULTY_BADGE` + `DIFFICULTY_FILTERS`
- 更新 `CollectionPage.tsx`：同上
- 更新 `article/[slug]/page.tsx`：删除内联三元表达式，改用 `getBadgeClass()`

**效果**: 新增难度等级只改 1 个文件。改配色只改 1 个文件。8 个消费者自动同步。


### 修复 2：CSS 变量补全（commit `197d07f`，同一 commit）

**问题**: 项目中 44 个独立色值散落在 JSX 里，换主题需逐个文件修改。

**做法**:
- `globals.css` 的 `:root` 里从 6 个 CSS 变量补全到 46 个
- 按语义分组：Surface/Text/Border/Accent/Scrollbar/Difficulty × 3/Topic × 4
- scrollbar 和 `::selection` 的硬编码 hex 同步替换为 `var()` 引用

**效果**: CSS 变量已就绪，组件后续可逐步从内联 `bg-[#xxx]` 迁移到 `bg-[var(--xxx)]`。


### 修复 3：提取通用 Toggle 组件（commit `2b4b835`）

**问题**: HighlightToggle 和 CloseReadingToggle 两个文件 99% 相同，纯复制粘贴。

**做法**:
- 新建 `Toggle.tsx`：纯 UI 组件，接收 `enabled`/`onToggle`/`label` 三个 props
- `HighlightToggle.tsx` 和 `CloseReadingToggle.tsx`：22 行 → 14 行，变为薄 wrapper，从各自 Context 取值后传给 Toggle
- Toggle 是第一个使用 CSS 变量的组件（`var(--color-accent-dark)` 替代 `#B08844`）

**效果**: 改开关样式只改一处。加新开关只需 10 行 wrapper。所有 toggle 视觉一致。


### 修复 4：词汇表加载提升（commit `9ea05ff`）

**问题**: 3 个组件（ArticleReader、WordPanelWrapper、KnownWordsPage）各自独立调用 `loadVocab()`，各自显示独立 spinner。

**做法**:
- 新建 `VocabContext.tsx`（Provider + `useVocab()` hook），在应用启动时加载词汇表一次
- `layout.tsx` 中挂载 `VocabProvider`
- 3 个消费者删除本地 `useState + useEffect + loadVocab`，改用 `useVocab()`

**效果**: 词汇表一次下载，全应用共享。3 个 spinner 合并为 1 个。消除模块级全局变量 `vocabCache`。


### 修复 5：Storage helper 提取（commit `9ea33a4`）

**问题**: 18 个 storage 函数各自重复 try/catch + JSON.parse + JSON.stringify 样板。

**做法**:
- 提取 `read<T>()` / `write()` / `today()` 三个内部 helper
- 18 个函数用 helper 重写，消除重复样板
- 公共 API（函数名、签名、行为）完全不变

**效果**: 每个函数的意图更清晰。将来改进错误处理逻辑只需改 helper。


### 修复 6：命名统一（commit `093defa`）

**问题**: 函数命名风格不一致——`markKnown`（无 As）vs `markAsRead`（有 As）vs `saveWordToCollection`（啰嗦）。

**做法**:
- `markKnown` → `markWordKnown`，`unmarkKnown` → `unmarkWordKnown`
- `markAsRead` → `markArticleRead`，`unmarkAsRead` → `unmarkArticleRead`
- 所有函数统一为 `verbNoun` 模式（动词 + 操作对象）
- 更新 4 个消费者引用
- `ArticleReadMarker` 添加 `displayName = 'ArticleReadMarker'`（React DevTools 可见）

**效果**: 一看函数名就知道操作对象是 Word 还是 Article。DevTools 能定位隐形组件。


### 修复 7：拆分 AppContext（commit `1f43d1e`）——最大改动

**问题**: 一个 AppContext 管理 6 个功能域，25 个值，13 个消费者。任何值变化全量重渲染。

**做法**:
- 拆成 3 个独立 Context，每个有自己的 Provider + hook：

| Context | 文件 | 管理内容 |
|---------|------|---------|
| KnownWordsContext | `src/context/KnownWordsContext.tsx` | 熟词管理（knownWords, knownWordDates, markWordKnown, unmarkWordKnown）|
| CollectionContext | `src/context/CollectionContext.tsx` | 收藏管理（savedWords + savedArticles 及其 CRUD）|
| ReadingContext | `src/context/ReadingContext.tsx` | 阅读模式（highlight/closeReading/selectedParagraph/readArticles）|

- `layout.tsx` 中嵌套 3 个 Provider
- 13 个消费者各取所需，不再全量订阅
- 删除旧 `AppContext.tsx`

**效果**: 精准重渲染——点高亮开关只刷新 ReadingContext 的订阅者，不影响 KnownWords/Collection 的订阅者。每个 Context 60-80 行，单一职责。加新功能（如笔记）只需新建一个 Context。


### 修复 8：Storage 抽象层（commit `826ee43`）

**问题**: Storage 层是黑箱——key 常量不公开，helper 不公开，无架构文档。

**做法**:
- `STORAGE_KEYS` 改为 `export`，外部可引用而非硬编码 key 字符串
- `readJSON` / `writeJSON` 改为 `export`，测试/迁移脚本可直接使用
- 添加 `StorageKey` 类型（key 的类型安全版本）
- 顶部添加架构注释：说明换后端 API 只需改 `readJSON`/`writeJSON` 两个函数，其余不变

**效果**: Storage 层的设计意图和升级路径写在代码里，新人不需通读 18 个函数就能理解架构。

## 四、经验总结

1. **先诊断，后动手。** 审查报告列出了 12 个问题并按严重度和修复难度排序，每步目标明确，否则容易"修了一个 bug 引入三个 bug"。

2. **每次只改一个关注点。** 8 个修复各自独立 commit，如果某个改动引入问题，`git bisect` 能精准定位到具体 commit。

3. **基础设施先行。** 先建立统一配置和 CSS 变量（Round 1），再改组件（Round 2），最后改架构（Round 3）。如果顺序反了，组件改完才发现配置没统一，就得回头再改。

4. **保持向后兼容。** 比如 `vocab.ts` 用重新导出的方式保留旧函数签名，消费者不需要同步改 import 路径。过渡平滑，typecheck 随时可验证。

5. **CSS 变量需要"桥梁"。** 变量定义了但组件不用就是摆设。Toggle 组件是第一个用 `var(--color-accent-dark)` 的组件，后续应逐步将其他组件的内联 `bg-[#xxx]` 改成 `bg-[var(--xxx)]`。
